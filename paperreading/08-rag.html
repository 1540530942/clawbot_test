RAG：把知识放到模型外面Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks

模型把知识写死在权重里，又错得很流畅，更新还要重新训练。RAG 把一个可替换的文档索引接到生成器前面，并让检索和生成一起端到端训练。实验里最漂亮的一幕：不用重新训练，只把维基百科从 2016 版换成 2018 版，模型给出的答案就跟着变了。

它要解决什么问题

语言模型的知识都写死在权重里，这带来三个工程问题。第一，事实容易错，而且错得很流畅：模型不会告诉你它不知道。第二，更新代价高：世界变了，只能重新训练。第三，无法核对：一个答案从哪里来的，没有出处。

另一方面，信息检索领域早就有了能直接查最新文档的系统，只是它们只能抽取原文片段，不能自由生成。论文要做的是把两者接到一起，让模型同时拥有两种记忆：权重里的“参数记忆”和可以随时替换的“非参数记忆”。

当时已有的尝试多是分开训练检索和生成，或者专门为抽取式问答设计。这篇论文提出的是一个通用框架：检索和生成放在一起端到端训练，任意 seq2seq 任务都能用。这个名字后来变成了整个行业的通用词。

核心思路

流程很简单：用查询编码器把问题编码成向量，在文档索引里做内积检索，取 top-k 篇，再把问题和每篇文档分别拼起来交给 BART 生成。

关键在于训练方式。论文不要求标注哪篇文档是对的。损失是目标序列的负边缘对数似然，把文档当成隐变量求和掉：

p(y|x) ≈ Σz∈topk pη(z|x) · pθ(y|x, z)

文档概率 p(z|x) 来自内积分数。生成得好的文档，下一轮会被推高。梯度就这样一路传到了查询编码器，让它学会“为了生成正确答案应该检索什么”，而不只是“和问题相似”。

为什么文档编码器不动

只有查询编码器在训练，文档编码器和索引保持不变。这是为了工程可行性：重新训练文档编码器就要重建 2100 万篇文档的索引，每一步都这么做完全不现实。

两种变体：只差一个顺序

直接用数字算一下，就能看到区别。假设两篇文档各讲一件事，目标序列是 [A, B]：

import numpy as np
doc = np.array([0.6, 0.4])            # 检索器给两篇文档的概率
# 每篇文档下，生成器给目标序列 [A, B] 每个 token 的概率
gen = np.array([[0.9, 0.1],           # 文档 1 只讲 A
                [0.1, 0.9]])          # 文档 2 只讲 B

rag_sequence = (doc * gen.prod(axis=1)).sum()    # 先整句连乘，再按文档求和
rag_token    = (doc @ gen).prod()                # 每个 token 先按文档求和，再连乘
print(f"RAG-Sequence p(A,B) = {rag_sequence:.4f}")
print(f"RAG-Token    p(A,B) = {rag_token:.4f}")

RAG-Sequence p(A,B) = 0.0900
RAG-Token    p(A,B) = 0.2436

RAG-Token 给这条序列的概率高出一倍多，因为它能先从文档 1 取 A，再从文档 2 取 B。RAG-Sequence 只能选一篇文档走到底，所以需要跨文档拼事实时会吃亏。

解码也因此不同。RAG-Token 可以用标准的束搜索，每个词的转移概率已经按文档求和过了。RAG-Sequence 则要对每篇文档各跑一次束搜索：要准确计算候选的概率，就要再对“这个候选没有进入其束”的文档做额外前向（Thorough Decoding）；或者把这些概率近似为 0（Fast Decoding），省掉这些计算。论文发现后者在长答案任务上并没有明显变差。

索引的代价

索引来自 2018 年 12 月的维基百科，切成互不重叠的 100 词片段，共 2100 万篇。论文写明是 2100 万个 728 维向量，共 153 亿个数值。按每个 32 位浮点算约 61GB。加上 HNSW 图结构，需要约 100GB CPU 内存，用 FAISS 压缩后可降到 36GB。

这说明 RAG 的代价和模型不一样。模型的代价是 GPU，RAG 的代价是一台大内存机器，而且更新数据不需要重新训练，只需要更新索引。整个可训练部分约 626M 参数。作为对比，论文提到 770M 的 T5-Large 在 NQ 上只有 28.9，RAG-Sequence 是 44.5。

最小检索

检索本身的核心只有几行。下面用 TF-IDF 代替 DPR，形式上和论文一样是内积检索加 softmax。文档是我写的几条机器人说明：

import numpy as np, re
docs = ["The ultrasonic sensor reports distance by echo time and has a blind zone under 2 cm.",
        "Mecanum wheels let the chassis strafe sideways without turning the body.",
        "The IMU drifts over time, so yaw should be corrected with visual odometry.",
        "Raspberry Pi 5 throttles above 85 degrees Celsius without active cooling.",
        "Battery voltage below 6.8 volts triggers a low power shutdown of the motors."]
tok = lambda s: re.findall(r"[a-z0-9]+", s.lower())
vocab = sorted({w for d in docs for w in tok(d)}); idx = {w: i for i, w in enumerate(vocab)}
def tf(s):
    v = np.zeros(len(vocab))
    for w in tok(s):
        if w in idx: v[idx[w]] += 1
    return v
D = np.stack([tf(d) for d in docs])
idf = np.log((1 + len(docs)) / (1 + (D > 0).sum(0))) + 1
def embed(s):
    v = tf(s) * idf
    return v / (np.linalg.norm(v) + 1e-9)
E = np.stack([embed(d) for d in docs])      # “索引”：离线算好，之后只读

def retrieve(query, k=2, temp=0.1):
    s = E @ embed(query)                    # 内积检索，和 DPR 的形式相同
    top = np.argsort(-s)[:k]
    p = np.exp(s[top] / temp); p /= p.sum() # p(z|x)：分数转成文档概率
    return [(round(float(q), 3), docs[i][:48]) for q, i in zip(p, top)]

for q in ["why does the yaw drift", "how close can the ultrasonic sensor measure", "does the pi overheat"]:
    print(q, "->", retrieve(q))

why does the yaw drift -> [(0.827, 'The IMU drifts over time, so yaw should be corre'), (0.173, 'Mecanum wheels let the chassis strafe sideways w')]
how close can the ultrasonic sensor measure -> [(0.934, 'The ultrasonic sensor reports distance by echo t'), (0.066, 'Mecanum wheels let the chassis strafe sideways w')]
does the pi overheat -> [(0.714, 'Raspberry Pi 5 throttles above 85 degrees Celsiu'), (0.286, 'Mecanum wheels let the chassis strafe sideways w')]

这里的 TF-IDF 只能匹配相同的词。DPR 的价值在于用 BERT 编码，能匹配含义相近但用词不同的文本。这个差距也体现在下一节的 BM25 消融里。

RAG-Token 在事实性上明显胜出，42.7% 对 7.1%。这个实验比分数更能说明问题：RAG 能减少幻觉。

索引换了，知识就变了

这是全文最漂亮的实验。挑 82 位在 2016 到 2018 年间换人的世界领导人，问“谁是某某职位”。同一模型搭配不同索引，给出的答案就跟着索引变。知识真的被搬到了模型之外。

端到端微调查询编码器比冻结的 DPR 好，语义检索又比 BM25 好得多。但 FEVER 上 BM25 反而最好，作者解释说这类声明以实体为中心，关键词匹配就很适合。这条很实用：先看你的查询是什么样的，再决定要不要语义检索。

影响与后续

  • 成了一个行业词。今天的 RAG 大多是工程化的流水线：切块、嵌入、向量库、重排、提示拼接。名字来自这篇论文，但训练方式已经完全不同。
  • 最大的变化是不再端到端。论文里检索和生成共同训练，而现在通常分开：用现成的嵌入模型和向量库，大模型也不微调，只把检索结果写进提示。这正是 GPT-3 带来的变化：任务写进提示，不用再训练。
  • 延续下来的。k 个文档、片段化、内积检索、HNSW，都还是今天的标配。
  • 今天的方向。Agent 式检索让模型自己决定何时查、查什么，这和 ReAct（第 17 期）是一脉相承的。

局限与争议

  • 检索可能“坍缩”。论文提到，在故事生成等任务上，模型可能学会忽略文档，表现退回到普通 BART，附录 H 专门说了这个现象。
  • 和检索无关的问题，加检索也没用。论文试了“空文档”机制，让模型知道什么时候不需要检索，但效果没有提升。
  • 幻觉只是减少，不是消除。“都差”一栏还有 17.7%。而且检索来源本身就可能有错，论文自己也说，维基百科或任何外部知识都不可能完全真实和无偏。
  • 分块是粗糙的。固定 100 词切分很容易切断上下文，这一点在工程实践里已经成了调优的主要内容。
  • 评测基线不同。表 2 中的很多“最好”结果用到了黄金证据，和 RAG 不是同一个条件。

和你的关系

这期直接对应仓库里登记过的任务 “加上 RAG”。建议先不做微调，走今天的工程路线：把机器人说明、传感器参数和故障记录切成小块，查询时放进 llm_manager 的提示。这部分放在云端就好，向量库不应占用树莓派的内存。

BM25 这条值得先试。机器人文档里全是型号、引脚、错误码这种精确实体，正是关键词检索擅长的。先上 BM25，效果不够再加语义向量，能省不少内存。最后别忘了索引热替换的启示：设备状态这种会变的信息，应该放在检索里，而不是写死在提示里。
