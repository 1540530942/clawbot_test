LoRA：只训练两个小矩阵LoRA: Low-Rank Adaptation of Large Language Models

微调 GPT-3 要 1.2TB 显存，每个任务存 350GB。LoRA 冻结全部权重，只在旁边训练两个小矩阵，它们的乘积就是更新量。只改注意力的两个矩阵，用不到万分之一的参数，就达到甚至超过了全量微调，checkpoint 也从 350GB 变成 35MB。

它要解决什么问题

GPT-3（第 6 期）之后，微调开始变得难以承受。全量微调 GPT-3 需要约 1.2TB 显存（要存权重、梯度和优化器状态），一次保存 350GB。假如有 100 个任务或者用户，就要 35TB 存储。

当时的替代方案都有明显短板。Adapter 在结构里加小模块，推理会变慢；Prefix tuning 只学一段虚拟前缀，部分任务掉分明显；也有方法只训练最后一层，表达能力又不够。论文的目标是找到一个方案，同时满足四点：参数少、效果不掉、不增加推理延迟、结构不用变。

核心思路：更新量是低秩的

作者猜想：在一个预训练好的模型上，为一个新任务微调所需的更新量 ΔW，本质上秩很低。这个直觉来自模型过参数化的研究：大模型里能做的事情很多，但适配某一个任务，只需要在少数方向上调整。

W = W0 + (α/r) · B·A W₀ 冻结；A 高斯初始化；B 初始化为 0

这个公式里有几个小设计很关键：

  • B 初始化为 0：训练开始时 BA=0，模型和预训练完全一致。所以从第一步起就是在原模型上微调，不会被随机噪声破坏。
  • 缩放 α/r：改变 r 时不需要重新调学习率。论文说 α 就设成第一个尝试的 r，之后不再调。
  • 只改注意力的 q 和 v：大多数实验只改这两个矩阵，MLP 都冻结，这是实验下来效果最好的配置。
  • 推理前合并：把 BA 加回 W₀ 之后，结构和原模型完全一样，没有任何额外延迟。
为什么它胜过 Adapter

Adapter 把一个小模块串在网络中，推理时一定要多算；LoRA 把它并联在原来的矩阵旁，训练完直接加回去，就没有额外的路径了。论文测出 GPT-2 Medium 推理：LoRA 和全量微调都是 19.8ms，Adapter 是 23.9 到 25.8ms，多了 20% 到 30%。

r 可以小到什么程度

这是全文最出人意料的一张图：r=1 意味着每个矩阵的更新量只有一个方向。这也支持了作者的猜想。不过这是“只改 q、v”这个配置下的结果，论文还指出，r 的影响和任务相关，并非一定是越小越好。

自己跑一下：低秩猜想是否成立

为了直观理解这件事，我写了一个最小实验。一个 64×64 的线性层，真实的更新量是秩 4 的，加少量噪声，分别用 LoRA 和全量微调拟合，看测试误差（1.0 表示和原模型一样差，越小越好）：

import numpy as np

class LoRALinear:
    """y = W0·x + (α/r)·B·A·x，W0 冻结，只训练 A、B"""
    def __init__(self, W0, r, alpha, rng):
        self.W0, self.s = W0, alpha / r
        self.A = rng.normal(0, 1 / np.sqrt(W0.shape[1]), (r, W0.shape[1]))
        self.B = np.zeros((W0.shape[0], r))           # B 全零：刚开始和原模型完全一样
    def __call__(self, X):
        return X @ self.W0.T + self.s * (X @ self.A.T) @ self.B.T
    def merged(self):                                 # 推理前合并，没有额外延迟
        return self.W0 + self.s * self.B @ self.A
    def params(self):
        return self.A.size + self.B.size

def adam(params, grads, st, lr=3e-3, b1=.9, b2=.999):
    st["t"] = st.get("t", 0) + 1
    for i, (p, g) in enumerate(zip(params, grads)):
        m = st.setdefault(("m", i), np.zeros_like(p)); v = st.setdefault(("v", i), np.zeros_like(p))
        m[:] = b1 * m + (1 - b1) * g; v[:] = b2 * v + (1 - b2) * g * g
        p -= lr * (m / (1 - b1 ** st["t"])) / (np.sqrt(v / (1 - b2 ** st["t"])) + 1e-8)

Adam，1200 步，全批量。误差以不微调时为 1.0 归一化。这是合成数据上的玩具实验，真实更新量是我设定的秩 4，用来说明机制，不是论文结果。

样本充足时（500 条），结果很干净：r 小于真实的秩 4 时拟合不了（0.60、0.31），r 到 4 之后误差就归零了，再加大也没有收益。这和论文秩消融的形状一致。

样本很少时（32 条，少于维度 64），结果没有我原来预想的那么简单。所有方案都拟合得不好，r=16 的 0.465 略好于全量的 0.544，但 r=4 的 0.638 反而更差。所以这个玩具实验没有复现论文里 LoRA 在少样本上胜出的结果。可能的原因是：样本这么少时，秩 4 的两个小矩阵也很难优化到位。这也提醒我们，论文里的少样本优势来自真实任务和预训练模型，不能简单理解成“低秩一定更抗过拟合”。

影响与后续

  • 开源微调的标配。Llama 系模型出现后，个人和小团队能负担的微调几乎都是 LoRA。Hugging Face 的 PEFT 库也从这里开始。
  • 从文本走向了图像。LoRA 在 Stable Diffusion 社区非常流行，用来存放特定风格，文件只有几 MB，还可以混合使用。
  • 量化微调。QLoRA 证明了把基座模型量化后也能用 LoRA 训练，进一步降低了显存门槛。
  • 服务形态。一个基座模型挂多个 LoRA，按请求切换，这也是今天很多微调 API 的方式。

局限与争议

  • “低秩”是实证结果，不是证明。论文没有从理论上证明更新量必然是低秩的。任务和基座差得很远时，这个假设可能不成立。
  • 批量合并。如果一个 batch 里要用不同的 LoRA，就不能把它们合并进权重，这时会有延迟，也会占显存。
  • 基座的显存还是省不了。论文里训练仍需要 350GB，因为基座参数要留在显存里。这一步后来靠量化解决。
  • 配置依赖实验。只改 q、v 是这篇论文实验下来的结果，今天很多实践也会把 k、o 或者 MLP 加进去，具体怎么选仍要根据任务实测。
  • 合并后不能轻易拆开。合并到权重后，想再切换任务就要保留原始权重或反向减回去，这有数值精度问题。

和你的关系

Qwen 这类模型在 DGX Spark 上微调时，LoRA 是最自然的方案。比如让 llm_manager 适应你的机器人指令和 JSON 结构，一个 r=8 的 adapter 只有几十到一两百 MB，在树莓派端和云端都比较好分发。这个大小要按实际模型算。

论文的少样本结果对你有参考价值：真实机器人数据肯定不多，可以优先试 LoRA，并和全量微调实测对比，毕竟上面的玩具实验里这个优势并没有自动出现。另外可以按技能分开存多个 LoRA，在云端按任务切换，这是我的建议，需要结合具体的模型规模和切换延迟再评估。
