投机解码：小模型猜，大模型批Fast Inference from Transformers via Speculative Decoding

大模型必须一个字一个字写，很难并行。投机解码让小模型先猜一串，大模型一次检查，通过巧妙的接受规则保证输出分布不变。T5-XXL 上提速 2.3 到 3.4 倍，输出分布完全一样。今天它已是推理框架的标配。

这篇论文在说什么

大模型生成文字时，要等每个字算完才能算下一个，很难并行。可是很多字其实很容易猜：“中华人民共”后面基本就是“和国”。为什么一定要动用大模型呢？

2022 年，谷歌提出投机解码：让一个小模型先快速猜几个字，大模型一次性检查。猜对了就全部留下，这样快了 2 到 3 倍，而输出的概率分布和原来完全一样。今天几乎所有推理框架（包括你用的 vLLM）都支持这个方法。

旧方法的问题

大模型的并行问题在于：写第 5 个字前必须知道第 4 个字。这叫自回归。就算有很多 GPU，这个顺序也无法并行。

生活中的类比

老教授写一本书。他很慢，但水平高。他让助理先写初稿，然后自己一次读完几句：前面的都没问题就直接通过，遇到第一处不好的就改掉，后面再让助理重新写。读一遍比自己写一遍快得多。这个比喻和处理器的“分支预测”也很像，论文的灵感正来源于此。

核心思想：猜、检查、修正

  1. 小模型自己连续写 γ 个字。这很快。
  2. 大模型一次把这 γ 个位置都算出来。为什么可以一次算？因为这时候前面的字都已经有了（是猜的），可以并行。
  3. 从头开始检查，遇到第一个被拒绝的就改掉，并丢弃后面的。

就算全部猜错，也至少能得到一个新字，所以大模型的调用次数绝不会比原来多。代价是做了一些白工。

数学：为什么结果完全一样

大模型给某个字的概率是 p，小模型是 q。接受规则是：

接受概率 = min( 1, p / q )
p
大模型的概率（我们真正想要的）。
q
小模型的概率。
情况一：p = 0.6，q = 0.3
  1. p/q = 2，取 min 后是 1，一定接受。小模型低估了这个字。
情况二：p = 0.2，q = 0.5
  1. p/q = 0.4，有 40% 的概率接受。小模型高估了。
  2. 最终这个字来自猜测的概率 = 0.5 × 0.4 = 0.2，正好等于 p。

被拒绝时，从“剩余分布”里重新抽一个：

p′(x) ∝ max( 0, p(x) − q(x) )

意思是：只从大模型比小模型更喜欢的那些字里抽。两部分加起来，每个字的最终概率都正好是 p。这就是论文证明的：

P = min(p, q) + (p − min(p, q)) = p
用情况一验证
  1. min(0.6, 0.3) = 0.3（猜到且接受）
  2. p − 0.3 = 0.3（靠拒绝后的重抽补上）
  3. 总和 0.6，等于 p

能提速多少

提速 = (1 − αγ+1) ÷ ( (1 − α) · (γc + 1) )
α
猜测被接受的概率。
γ
一次猜几个。
c
小模型的成本和大模型的比。
α = 0.75，γ = 7，c = 0.02
  1. 分子：1 − 0.75⁸ ≈ 0.90
  2. 第一个分母：1 − 0.75 = 0.25，于是平均每轮得到约 3.6 个字
  3. 第二个分母：7 × 0.02 + 1 = 1.14
  4. 提速 ≈ 3.16 倍。论文的实测是 3.4 倍。
动手试试：猜几个字最划算

这是论文的公式。α 是一个 token 被接受的概率，γ 是一次猜几个，c 是小模型相对大模型的成本。论文实验里 c 都小于 0.05。

影响和局限

影响：现在是推理框架的标配（vLLM、llama.cpp 等）。后来还有不用小模型的 Prompt Lookup，也属于这条路。

局限（论文）：

  • 要额外算力。没有额外并行资源时，帮助不大。
  • 总计算可能增加。拒绝的部分都是白算。
  • 提速取决于接受率。有创造性的高温采样下接受率会下降。
  • 束搜索没有解决。论文留作未来工作。

和你的机器人的关系：llm_manager 输出的 JSON 里有很多固定结构，接受率会比较高，所以很适合用。你在 spark 上用 vLLM 跑 Qwen 时，可以试试用小模型做草稿。在树莓派上就算了，第二个模型也要占内存。规划任务的 8 秒预算里，提速 2 倍很有价值。

一句话总结：让小模型先猜，大模型只负责检查；猜对就赚，猜错也不亏，而且结果和原来完全一样。
